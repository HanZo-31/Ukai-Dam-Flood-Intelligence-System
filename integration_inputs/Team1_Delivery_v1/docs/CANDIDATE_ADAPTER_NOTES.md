# Candidate adapter notes (contract 1.0.0, stored lookup only)

* One module knows the contract: `frontend/src/lib/candidate.ts` (types, request builder, capability reader, result validation, client); `candidateRun.ts` submits and follows queued/running states; `hooks/useCandidate.ts` holds UI state (latest-request-wins, last good result kept); `pages/WhatIf.tsx` is the only page using them.
* Base URL: same-origin `/api/v1/candidates`. Dev (`DEV_FRONTEND.cmd`, port 5175): `vite.config.ts` forwards it to `127.0.0.1:8770`. Production server: **not routed yet**, see `patches\ssd_web_server.candidates.PATCH.md`; until applied the page reports "candidate service unavailable" and everything else works.
* Reference resources in a result must start with `/api/v1/prototypes/scenarios/<source_scenario_id>` and are opened through the reference API (port 8766 path), never through the candidate base.
* The adapter rejects (does not display) a result whose request_id, mode, family or requested peak differ; an exact selection that returns another peak; a nearest selection that is not the nearest stored peak (ties lower); `computed` not false; `scientifically_validated` true; calibration not `uncalibrated`; an unknown source scenario.
* **Schema aligned (8 Oct 2026).** Team 2's `candidate-openapi-v1.json` and `candidate-examples.json` were received and are kept unchanged in `source_overlay\frontend\src\lib\fixtures\`. The reader now uses the real capabilities fields (`supported_modes`, `stored_peaks_m3s`, `selection_range_m3s`, `experimental_ml_enabled`, `model_unavailable_reason`, `calibration_status`); result checks now also require `completed_at` and `timing_scope`, all five reference-resource keys, a returned peak that is one of the stored peaks, and the schema's request-ID pattern (must start with a letter or digit). `lib/candidate.contract.test.ts` checks the adapter against both files (field lists, ID pattern, bounds, the four example calls). Other plausible capability shapes are still accepted in tests and enable nothing unless a mode is declared. This is agreement with the published schema and examples, not a test against a running service.
* Fixtures (`testing/candidateFixtures.ts`) are labelled "FIXTURE" and imported only by tests.
* Real-service checks still to do: GET capabilities; POST 20000 exact; POST 26000 without and with `allow_nearest_stored`; repeat the same request ID (same content: same job; different content: 409); GET unknown job (404); stop the service mid-session and recover.
